# LeakSanitizer suppressions for the unit tests and the stress scenarios run
# against a build with NSCP_SANITIZE=address.
#
# Format (one per line):
#   leak:<symbol or library substring>
#
# Module load-time global state (helper_singleton -> core_wrapper -> pimpl,
# per-module static strings, etc.) allocated while a plugin .so runs its
# static initializers under dlopen. NSClient++ modules export STB_GNU_UNIQUE
# symbols (C++ template/inline statics), which makes glibc mark them NODELETE:
# dlclose never unmaps them, so their destructors run only in _dl_fini at
# process exit — *after* LSan's leak check. The state is one-per-module and
# bounded (NODELETE => loaded at most once), and it IS reclaimed at exit, so
# this is a shutdown-ordering false positive rather than a real leak. Every
# such allocation passes through the plugin loader's load_dll/dlopen path.
leak:nsclient::core::dll_plugin::load_dll

# The CPython runtime behind PythonScript. python_script::init() brings the
# interpreter up once per process and python_script::destroy() leaves the
# Py_FinalizeEx() call commented out, so every process that loads the module -
# the agent, and each `nscp settings` run that boots the enabled plugins -
# exits with the interpreter state still allocated: the imported encodings
# and io modules, the codec registry, the type caches. LSan then reports a
# few hundred allocations and 400 KiB per process, all reached through
# libpython. That is one bounded interpreter per process, not growth, and
# CPython does not free all of it even when it is finalized. Matched on the
# module name rather than python_script::init(), because the default 30-frame
# stack LSan captures often ends inside libpython before reaching our frame.
leak:libpython
